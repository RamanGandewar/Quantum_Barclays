# Known Limitations

## KEMTLS Depends On An OQS-Go Fork

KEMTLS is not supported by mainline Go's `crypto/tls` package today because mainline TLS authenticates servers through certificate signatures and the `CertificateVerify` message. KEMTLS changes the TLS state machine by authenticating with KEM decapsulation, removing `CertificateVerify`, and adding KEM ciphertext processing in a place where the standard library does not expose extension points. An OQS-Go fork changes the handshake implementation, certificate handling, and key schedule integration so ML-KEM-based authentication can be tested. Track upstream Go `crypto/tls` post-quantum issues and proposals before attempting to replace the fork with mainline Go.

## StrongSwan Native Mode Is Linux-Only

The VPN phase depends on StrongSwan, Linux kernel IPsec support, UDP ports `500` and `4500`, and elevated network capabilities such as `NET_ADMIN` and, for some deployments, `SYS_MODULE`. Docker Desktop on macOS and Windows runs containers inside a VM and does not provide the host-level kernel IPsec integration needed for a real StrongSwan tunnel. Developers on macOS or Windows can edit and validate the configuration templates, but native tunnel testing should run on a Linux VM, bare-metal Linux host, or cloud instance with the required kernel modules and capabilities enabled.

## Mutual TLS Is Outside Current Scope

The current verifier and dashboard model server-side migration state only. Adding mutual TLS in a PQC context would require issuing client ML-DSA certificates, validating client certificate chains, and recording client `CertificateVerify` evidence with an ML-DSA signature. The API models, CA automation, scanner evidence, server services, and dashboard identity views would need to change to distinguish server authentication from client authentication. The primary files to extend would be `backend/ca/generate_pki.py`, `backend/verifier-api/app/models.py`, `backend/verifier-api/app/adapters/`, `services/server-pqc/`, and `frontend/dashboard/src/main.tsx`.

## PQC OCSP And CRL Support Is Not Implemented

The CA automation produces certificate material and metadata, but it does not publish OCSP responses or CRLs for PQC certificates. IETF has no finalized, broadly deployed standard profile for PQC certificate revocation, and existing OCSP responder deployments commonly use RSA or ECDSA signatures, which weakens a PQC migration story if the revocation proof remains classically breakable. Until PQC revocation support is standardized and implemented across the selected TLS stack, the practical mitigation is to use short-lived certificates, automate reissuance, and keep revocation assumptions explicit in audit documentation.

## Demo Telemetry Audit Disclaimer

Use this exact wording in reports:

> Demo mode telemetry is generated by deterministic adapters and does not reflect real cryptographic negotiation. It must not be presented as evidence in a security audit, compliance assessment, or regulatory filing. For audit evidence, enable native mode and attach OpenSSL provider algorithm listings, real certificate chains with openssl verify output, packet captures with SSLKEYLOGFILE policy documented, and StrongSwan ipsec status output.

## Missing Post-Quantum SSH Standard

No finalized RFC defines ML-KEM-based SSH key exchange or ML-DSA host-key authentication as a production standard. OpenSSH has merged support for `sntrup761x25519-sha512`, which is a hybrid using NTRU Prime rather than ML-KEM. The IETF draft `draft-kampanakis-curdle-ssh-pq-ke` covers ML-KEM hybrid SSH key exchange, but it is not yet an RFC. This project's SSH mode uses experimental labels such as `X25519MLKEM768` and `ml-dsa-65` that align with the intended migration direction but may not match the final standard names or wire format.
